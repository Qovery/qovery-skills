## PHASE 1: Understand Portal Requirements

### 1.1 Authenticate

Use the same authentication flow as the other Qovery skills:
1. Check if `QOVERY_CLI_ACCESS_TOKEN` or `QOVERY_API_TOKEN` is set in the environment
2. If not, check if the CLI is authenticated: look for `~/.qovery/context.json`
3. If the CLI is authenticated, generate a token via `qovery token --name "builder-portal"`
4. As a fallback, use the CLI's JWT token from `~/.qovery/context.json`

### 1.2 Check for Existing Builder-Env Setup

The portal depends on the builder platform being set up first. Look for the `builder-platform-config.yaml` file:

```bash
# Check common locations
ls builder-platform-config.yaml 2>/dev/null \
  || ls qovery-builder-platform/builder-platform-config.yaml 2>/dev/null \
  || ls ../qovery-builder-platform/builder-platform-config.yaml 2>/dev/null
```

**If found:** Read it and extract the configuration (organization ID, cluster ID, blueprint env IDs, isolation mode, TTL settings).

**If NOT found:** Tell the user:
> "The builder platform hasn't been set up yet. I need the `builder-platform-config.yaml` file generated by the qovery-builder-env skill.
>
> Say **'Set up builder environments for non-tech teams'** or run `/qovery-builder-env` to set up the platform first, then come back to deploy the portal."

STOP here if the config file is not found.

### 1.3 Portal Configuration

Ask the platform engineer about the portal settings:

1. **Custom domain?** — e.g., `builder.company.com`, `workspace.company.com`
   - If not provided, the portal will be accessible via the default Qovery-generated URL

2. **SSO provider?** — How should builders authenticate?
   - **Google Workspace** — most common for Google-based organizations
   - **Okta** — enterprise SSO
   - **Azure AD (Entra ID)** — Microsoft-based organizations
   - **Generic OIDC** — any OpenID Connect provider

3. **Branding:**
   - Company name (displayed in the header and login page)
   - Primary color (hex, e.g., `#2563EB` — used for buttons, accents)
   - Logo URL (optional — displayed on the login page and header)

4. **Max environments per builder?** — How many environments can each builder create?
   - 1 (strict — one workspace per builder)
   - 3 (recommended — allows multiple projects)
   - 5 (generous)
   - Unlimited (no limit — use with caution)

5. **Templates to expose?** — Which blueprint environments should builders be able to choose from?
   - List the blueprint environments from the config
   - For each, ask for a display name, description, and icon
   - Example:
     > "I found these blueprint environments in your config:
     > 1. Blueprint env `xxx-xxx` — what should builders see this as?
     >    - Name: "Sales Tools"
     >    - Description: "Build CRM integrations and sales dashboards"
     >    - Icon: chart-bar"

6. **Can builders extend their TTL?** — If the environment is about to stop, can they extend?
   - Yes — specify maximum extension (e.g., +24h, +48h)
   - No — environments stop at the scheduled time, must be restarted manually

7. **Can builders delete their own environments?** — Or only the platform team?
   - Yes (recommended — keeps things clean)
   - No (platform team controls all deletions)
